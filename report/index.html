A single-GPU field guide and a heterogeneous multi-GPU tensor-parallel / data-parallel study. What actually runs out first when you serve a small fine-tuned model — and what changes when you add a second, bigger card on a slow interconnect. Every number is measured on one rig; read the caveats, they are the difference between quoting a number and understanding it.

The operating rules

Six findings carry the whole study. Everything after this section is the evidence and the caveats behind them.

  • Short-context concurrency becomes host-bound. On one A5000, aggregate throughput climbs to a broad plateau (C=32–64), peaks at ~802 tok/s at C=64, then declines — the limiter leaves the GPU (util median 94%→41%, power 229→168 W) while the server process CPU rises ~11×. §4
  • Long context flips the constraint to VRAM. Keep multi-turn sessions resident and KV cache (f16 = 144 KiB/token) becomes binding: "30 users" fits only as a q8_0-at-8k edge case. §6
  • Low-bit weights accelerate decode. Decode is bandwidth-bound (Q4_K_M is 2.18× bf16); prefill is compute-bound and flat across bit-width. §5
  • vLLM / SGLang win under concurrency. At matched bf16, C=1 is a tie (llama.cpp 61 ≈ vLLM 68); by C=64 vLLM and SGLang are ~4× llama.cpp. §7
  • Data-parallel is the dependable two-GPU throughput choice under load. Two independent replicas beat the best single card once enough concurrent work engages both; the margin grows with C (to 1.23× balanced, 1.38× prefill). §12
  • Tensor-parallel is a narrow low-concurrency tool with worse TTFT. It wins single-stream (~1.5× on balanced/decode) but erodes to near-parity or a loss under load, and always raises time-to-first-token. §12
Scope — read before quoting anythingThis is one heterogeneous box (A5000 + A6000), no NVLink (nvidia-smi topo = SYS), cross-NUMA PCIe Gen3, a single 4B model, closed-loop (barrier-synchronous or finite-user-with-think-time, never open-loop Poisson arrivals), and hardware- and build-specific. Numbers do not transfer to other GPUs, interconnects, models, or arrival processes.

What was measured — and what the metrics mean

Two probe families, deliberately not comparable to each other. A saturation sweep is a barrier-synchronous, fully-backlogged closed loop (fixed prompt corpus, ignore_eos, --parallel == C): it measures capacity ceilings, not arrival latency. Locust runs a finite pool of users with think-time — more traffic-like, still closed-loop and throttled by the pool. The multi-GPU study uses a fixed-server / vary-client shape: each server boots once at NP = max(C) and the client sweeps concurrency. Definitions below are client-observed proxies, not kernel counters — that is exactly why the definitions matter.

Model & engines

  • Base: Qwen3-4B-Instruct-2507 (rev cdbee75f, Apache-2.0) — 4B params, 2560 hidden, 151,936 vocab, tied embeddings.
  • Fine-tune: legal-ops LoRA r=16, α=32, merged bit-exact into the base.
  • llama.cpp: serves Q6_K GGUF (~3.3 GB, 6.56 bpw), CUDA build 91d2fc3, f16 KV.
  • vLLM / SGLang: serve bf16 safetensors (models/merged); client + reporting on Python 3.14.

Metric definitions

  • Aggregate throughput = Σ completion_tokens / makespan over one global wall clock.
  • TTFT (prefill proxy) = time to first streamed token — includes HTTP, queueing, scheduling, prefill; not isolated prefill-kernel time.
  • Decode tok/s (decode proxy) = per-request median of (gen−1)/(latency−TTFT) — a user-visible rate, never summed across cards.
  • Fair-share = aggregate ÷ C, the throughput each user would see if split evenly.

3

The artifact is verified — and arbitrary checkpoint deltas are not LoRAs

Every measurement serves one merged checkpoint, and its provenance chain is verified rather than assumed. The merge loads base in bf16, forces the LoRA B@A product to FP32, computes it, then casts once to bf16 (merge_and_unload(safe_merge=True)) and re-ties the head. The recorded checks: merged q_proj is bit-exact base + (α/r)·BA across all 252 target tensors; tied embeddings preserved; no lm_head synthesized; chat-template SHA-256 match; GGUF filetype MOSTLY_Q6_K, general.architecture == qwen3, 151,936 vocab. Downstream: 0 failures across 2,620 requests in the 1/30/100 Work-A run, with tokens_predicted_total matching the client exactly.

Provenance honestyThe artifact's manifest records source_git_commit = null for the Work-A run — the model provenance is pinned, the exact code state of that run is not. Small, but stated.

Is a merged LoRA "just a matmul"? The SVD-extraction probe

Mechanically, yes: a merged LoRA is W + (α/r)·B·A — base weights plus a low-rank matmul. The tempting leap is "so I can subtract any two checkpoints, SVD the difference, and recover the LoRA that made it." The probe tests exactly that with a control (a delta we know is a rank-16 LoRA) and a treatment (the delta between two published checkpoints).

Mandatory framing — do not skip
  • It is an inter-checkpoint delta, not a proven full fine-tune. Instruct-2507 declares no base_model; its production process is not established from these artifacts.
  • Any rank-r SVD of a weight delta is "LoRA-representable," never "a working extracted LoRA" — no task behavior was trained or validated.
  • The high-rank result does not refute "LoRA can match full fine-tuning" (cf. Thinking Machines, LoRA Without Regret): a trained low-rank adapter stores task-relevant information, not the full weight delta — orthogonal to this measurement.
  • bf16 read-back inflates the floors: the control reads as eff-rank ~43 (not 16) and ~74% (not 100%) because bf16 rounding noise smears energy against a delta only ~0.2% of the base norm — the intended calibration baseline, applied to both deltas.
Takeaway: "merged LoRA = base + low-rank matmul" is true; "so I can SVD any diff back into a LoRA" is false in general — the real between-checkpoint delta is high-rank, embedding-shifting (~20%, which a target-linear LoRA cannot represent), and MLP-heavy.
4

One A5000 peaks at C=64 — but per-user experience degrades throughout

Method: llama.cpp, closed-loop barrier-synchronous load, ignore_eos, a fixed corpus averaging ~242 tokens (231–253) with exactly 256 generated tokens, --parallel == C, 768-token slots, f16 KV. A saturation-capacity probe, not a real arrival-pattern test.

Aggregate throughput rises to a broad plateau over C=32–64, peaks at C=64 = 801.8 tok/s (48,108 tok/min, 6.77× single-stream), then falls to 772.7 at C=96 and 749.3 at C=128. There is no simple "knee at 30": the biggest single batching win is C8→C16 (+262 tok/s), and marginal gain goes negative past 64 (C64→96 −29, C96→128 −23).

The per-user view collapses the whole way up

Fair-share throughput (aggregate ÷ C) falls from the first step: 118.4 → 12.5 at the C=64 peak → 5.9 at C=128 (a 20.1× degradation). Because each request emits a fixed 256 tokens, latency is its inverse: p50 climbs 2.18 s → 43.64 s. At the throughput peak, each user already waits ~20.4 s. TTFT p50 stays sub-second at every C, but the tail explodes (TTFT p95 0.08 s → 4.05 s, ~50×). "Throughput-optimal" and "latency-acceptable" are different operating points.

What breaks first: the bottleneck leaves the GPU

As C rises the GPU does less (util median 94%→41%, power 229 W→168 W, dipping to 141 W at C=96) while the llama-server process CPU rises ~11× (2.55%→29.13%). The GPU isn't idle — it is bursty and starved: p95 util pins at 99% while the median sits near 40%, a distribution consistent with gaps between batches. The evidence most strongly points to a host-side feed/orchestration bottleneck (CPU-scheduling the leading candidate); no profiler was run, so the exact mechanism is not isolated.

Measurement hygieneThe "MemCtrl proxy %" (nvidia-smi utilization.memory, 71→26%) is the fraction of time the memory controller was busy — a proxy, not achieved bandwidth in GB/s. It falls at high C simply because the GPU idles more between bursts. No bandwidth claim rests on it.

The 768-token f16 KV cache for Qwen3-4B is ~108 MiB, which is the slope. Extrapolating, ~195 slots would fill the board — but throughput peaks at C=64 and declines, so VRAM never binds before the peak in this regime. It is not the constraint here.

Precision buys decode speed; quality evidence is narrower than "accuracy"

These are single-stream llama-bench micro-benchmarks (raw kernel throughput: pp512 = prefill, tg128 = decode; no HTTP, no sampling, no real prompts) — a different quantity from the server numbers above. Two opposite lessons: decode reads every weight once per token so fewer bits = faster decode; prefill is a big batched GEMM, so it is compute-bound and does not order by bit-width.

KV dtype: a memory knob, barely a speed knob

q8_0 KV halves the KV footprint for ~3.7% decode / ~4.1% prefill loss (f16 128.62 → q8_0 123.90 tg128). bf16 KV is same size as f16 but slightly slower — prefer f16. The memory win only pays off at long context / high batch.

Long context flips the constraint from host scheduling to VRAM

Short-context serving (§4–§5) was not VRAM-bound. The moment you open the context window and keep sessions resident, capacity flips to VRAM-bound: how many bytes of KV cache you can hold. Two separate taxes — reserved window size sets what fits; actual KV depth sets how fast each token decodes.

Prefix caching flips the TTFT trend

With prefix caching on, deeper history raises the cache-hit rate and lowers TTFT; with it off, every turn reprocesses the whole prompt and TTFT climbs. Decode rate is untouched (~99.7–104.2 tok/s either way) — caching is purely a prefill/TTFT effect. Measured over 150 scripted-user turns replaying individual UltraChat conversations, server ctx 32768.

Engine choice changes with concurrency and deployment priorities

VOID → fixed (provenance)The original E5 attempt was VOID — vLLM 0.25.1 (torch 2.11 / triton 3.6 nightly) died at import (a Triton JIT parse bug), serving 0 requests. It is now resolved by pinning a stable stack (vLLM 0.11.0 / torch 2.8.0+cu128 / triton 3.4.0 / transformers 4.57.1). The failure stays in the record; the comparison below is the real, fair one.

Use vLLM / SGLang when…

  • many concurrent users on a GPU under latency SLAs
  • you want PagedAttention / RadixAttention + native continuous batching + prefix caching + speculative decoding
  • native multi-LoRA serving (many adapters, one base)

Use llama.cpp when…

  • single-user desktop / edge / offline, competitive at low concurrency
  • a quick prototype or model-swapping via GGUF, widest quant/hardware reach
  • CPU or mixed hardware, trivial deployment (one static binary)
Keep attachedbf16 on all three — not each engine's optimal config (llama.cpp's low-bit GGUF and vLLM's AWQ/FP8 paths would each shift their own curves). Prefix caching off (understates SGLang/vLLM). Iso-precision, not iso-configuration: SGLang ran with CUDA graphs disabled for startup robustness while vLLM used them — so SGLang is somewhat handicapped here. One 4B model, one workload. No engine is "inherently" fastest. For external context, a Red Hat test cites ~44× for vLLM — but on Llama-3.1-8B full-precision / single H200, a very different config the source itself calls workload-specific. Multi-turn KV reuse systems such as SwiftCache report up to −69% P99 TTFT vs vLLM/SGLang KV-cache baselines; production levers (speculative decoding, chunked prefill, prefix caching, disaggregated prefill/decode) live mostly in vLLM/SGLang, and typically move TTFT and effective concurrency more than picking a faster quant (see Inside vLLM).

Finite-user load is more traffic-like, but still closed-loop

Studies E2/E3 use Locust with a finite pool of users and think-time. More traffic-like than the barrier sweep, but not real traffic: still closed-loop, and offered load is throttled by the pool (E2 u20 = 2.07 req/s, u60 = 2.89 req/s), not pushed to saturation. Never compare these tok/s head-to-head with the §4 saturation numbers — they measure different regimes. Both experiments: 0 failures.

Scaling beyond one card: this is a heterogeneous SYS topology

The multi-GPU material is a second act, not an appendix — it materially changes the deployment recommendation. One host, two different cards on a slow interconnect. nvidia-smi topo -m = SYS: the cards communicate over PCIe + the cross-NUMA CPU interconnect (UPI). There is no NVLink. GPU0 sits on NUMA node 0, GPU1 on node 1; every run pins CUDA_DEVICE_ORDER=PCI_BUS_ID + a per-server CUDA_VISIBLE_DEVICES, and telemetry samples each physical card.

The two design axesTensor-parallel (TP) shards one model across both cards, exchanging activations every layer over PCIe. Data-parallel (DP) here runs two independent full replicas (one per card) behind a client-side join-shortest-queue router — not vLLM --data-parallel-size 2, which locksteps the fast card to the slow one on a no-NVLink pair (DP ranks all-reduce an "any-unfinished" flag and size KV uniformly). Two independent replicas let the A6000 profile its own larger KV cache and pull more load.

The topology and thermal taxes explain why throughput is not efficiency

Per-card telemetry at C=64 corrects three tempting assumptions. Both cards run ~87–91% utilization in TP and DP — the loss is not idle silicon. The two cards hit different limits: the A5000 is power-capped (at its 230 W board limit ~98% of samples), the A6000 is thermally throttled (sw_thermal_slowdown active in most high-C samples, 85–88 °C). DP is well balanced (both replicas ~91%, the A6000 drawing more power for its larger share).
